# 入力ソース別の読み方（source modes）

paper-comic は「論文」だけでなく，**ソースコード**，**実装途上の手法（文章＋コード）**，**エージェントとの議論ログ**からも同じスタイルの方法図解を作る．
どの入力でも最終的には共通の中間表現 `method-spec.md`（`references/method-spec.md`）にまとめ，そこから図を設計する．

| mode | 入力例 | 自動判定の手がかり |
|------|--------|------------------|
| `paper` | arXiv URL，PDF，論文テキスト | arxiv.org / .pdf / Abstract・Introduction 構成 |
| `code` | リポジトリのパス，GitHub URL，ファイル群 | ディレクトリ，`.py/.ts/.rs/...`，github.com |
| `design` | 研究計画・設計メモ（.md）＋途中のコード | TODO・未実装・「予定」「案」が混在，複数種の入力 |
| `discussion` | 現在のセッションでの議論，貼り付けた会話ログ，transcript ファイル（.jsonl） | 「さっきの議論」「この会話」，User/Assistant の往復，`.jsonl` |

複数の入力を同時に渡してよい（例：`plan.md` ＋ `src/` ＋ 今の議論）．その場合は `design` として統合する．
判定に迷ったら，確認メッセージの冒頭で「〇〇として読みました」と明示する．

---

## mode: paper

既存の手順（SKILL.md Step 1）どおり．コードが公開されていれば `code` の手順で読み，図の注記に `file:line` を添えてもよい．

## mode: code — ソースコードから方法を可視化

**目的**：コードを読まない人が「このコードは何を入力に，どの部品を通って，何を出すのか」「核心の処理は内部で何をしているのか」を図だけで理解できること．
ファイル構成図やクラス図を描くのではなく，**方法（アルゴリズム）として**描く．

### 手順

1. **地図を作る**：`python3 <SKILL_DIR>/scripts/code_map.py <repo> > code-map.md`
   - ファイル別の行数，クラス／関数（行番号付き），ローカル import の依存，エントリポイント，`TODO/FIXME/NotImplementedError/pass` の位置が出る．
   - GitHub URL の場合は `git clone --depth 1 <url> <作業ディレクトリ>` してから実行する．
2. **入口を特定**：README → エントリポイント（`train.py`，`main()`，CLI，`__main__`）→ 設定（config/yaml/argparse の既定値）．
3. **1本の実行経路をトレースする**：代表的な 1 回の forward / 推論 / 1 ステップの学習ループを追い，
   各段の **入力 → 処理 → 出力（テンソル形状・データ型・単位）** を書き出す．形状が静的に分からなければ config 既定値から推定し「推定」と記す．
4. **核心を見つける**：ベースライン実装と違う部分（独自モジュール，独自 loss，独自サンプリング等）がこのコードの「方法」．ボイラープレート（ログ，CLI，チェックポイント保存，分散学習の初期化）は描かない．
5. **根拠を残す**：method-spec の各コンポーネントに `path/to/file.py:L120-L168` の形で根拠を付ける．
6. **論文もある場合**：論文の記述とコードの差異（ハイパーパラメータ，順序，追加の正規化など）を `⚠ 差異` として記録する．図にも小さく出せる．

### code mode で推奨する図

| 図 | 内容 |
|----|------|
| 全体アーキテクチャ | 入力 → 主要モジュール → 出力．モジュール名はコード上の名前（`Encoder`，`RouterBlock`）を短く添える |
| データフロー／形状 | 1サンプルが通る経路と各段の形状 `(B, T, D)` の変化 |
| 核心モジュールの内部 | 独自部分の内部計算を分解（局所拡大，小さな数値例） |
| 学習／推論ループ | 1 step で何がどう更新されるか，loss の構成 |
| 設定ノブ | 振る舞いを変える主要ハイパーパラメータとその効く場所（必要時のみ） |

## mode: design — 実装途上の手法（文章＋コード）

**目的**：「いま何が決まっていて，何が実装済みで，何が未定か」を，一枚で共有・議論できる設計図にする．
研究の進行に合わせて何度も作り直す前提なので，**method-spec を正本にしてバージョン管理**する．

### 手順

1. 文章（研究計画，設計メモ，Issue，Notion ページなど）から，手法の構成要素・データの流れ・狙い・評価計画を抜き出す．
2. コードがあれば `code` の手順 1〜5 を行い，各構成要素の **実装状態** を判定する：

| 状態 | 判定基準 | 記号 |
|------|---------|------|
| implemented | 対応するコードがあり，呼び出し経路に入っている | ✅ |
| partial | スタブ，`TODO`，`NotImplementedError`，ダミー値，一部の分岐のみ | 🟡 |
| planned | 文章にはあるがコードがない | ⬜ |
| open | 方式が未決定，複数案が併存，文章とコードが矛盾 | ❓ |

3. 文章とコードが矛盾する場合は，どちらが新しいか（更新日時，git log）を見て判断し，判断できなければ `open` にして確認事項に入れる．
4. 前回の `method-spec.md` があれば差分（追加・削除・状態変化）を出す．

### design mode で推奨する図

| 図 | 内容 |
|----|------|
| 設計スナップショット | 手法全体の構成＋各要素の状態（✅🟡⬜❓）を視覚言語で表示．最重要 |
| 核心アイディアの機構図 | まだ実装途中でも，狙っている計算・仕組みを分解して描く |
| 決定と代替案マップ | 決まったこと（理由付き），捨てた案（✕），未決の分岐（❓） |
| 実装ギャップ／次の一手 | 未実装・部分実装の箇所と，次に着手すべき順序 |
| 評価計画 | 何と比べて何を測れば仮説が検証できるか（計画段階なら planned 表示） |

## mode: discussion — エージェントとの議論から可視化

**目的**：長い議論の「最終的に合意した構成」を取り出して図にする．議論の経過ではなく **結論の構造** を描く（必要なら決定の経緯を別図にする）．

### 議論ログの取得

| 状況 | 取得方法 |
|------|---------|
| 同じセッションで議論した直後 | 自分のコンテキストにある会話をそのまま使う |
| ユーザーが会話を貼り付けた／ファイルで渡した | それを使う |
| 過去のセッション（Claude Code） | `python3 <SKILL_DIR>/scripts/extract_transcript.py --latest claude --cwd <project>` |
| 過去のセッション（Codex） | `python3 <SKILL_DIR>/scripts/extract_transcript.py --latest codex --cwd <project>` |
| ファイルを直接指定 | `python3 <SKILL_DIR>/scripts/extract_transcript.py path/to/session.jsonl` |

`extract_transcript.py` はユーザー発言とアシスタントの本文だけを `[T12] User: ...` 形式の Markdown にする（ツール出力・システム文は除く）．
`--list claude|codex [--cwd <project>]` で候補セッション一覧を出せる．議論が長い場合は `--since T30` のように範囲を絞ってもよい（`--help` 参照）．

### 抽出ルール

1. 発言にターン番号を振り，以下を抽出する：
   - **構成要素**（モジュール，データ，損失，評価）
   - **決定事項**：何を，なぜ（根拠のターン番号）
   - **却下した案**：何を，なぜ却下したか
   - **未決事項**：保留・要検証・ユーザーが迷っている点
   - **アクション**：次にやると言ったこと
2. **後の発言が前の発言を上書きする**．撤回・修正された案は「却下」に回し，図の本体に描かない．
3. アシスタントの提案をユーザーが明示的に受け入れていない場合は「提案（未合意）」として `open` 扱いにする．勝手に決定事項にしない．
4. コードやメモが併せて渡されたら `design` と同じく実装状態も付ける．
5. **描く前に必ず method-spec の要約をユーザーに見せて確認する**（会話の解釈違いが一番起きやすいモードのため）．確認は図の範囲・枚数の確認と同じメッセージにまとめてよい．

### discussion mode で推奨する図

| 図 | 内容 |
|----|------|
| 合意した手法の全体像 | 最終的な構成を 1 枚で（未合意部分は ❓ 表示） |
| 核心メカニズム | 議論で最も時間を使った／最も新しい仕組みの分解 |
| 決定ツリー | 主要な分岐点ごとに：採用案・却下案・理由 |
| 未決事項とアクション | 次の議論・実装で詰めるべき点 |
